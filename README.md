# hello-talk

카카오톡 스타일 메신저. 화면 배치는 프로토타입에서 고른 **B안(관계에서 파생 · 새 목적지 없음)** 을 따른다:
하단 탭은 5개 그대로 두고, 선물하기와 일정은 별도 탭이 아니라 **사람과 대화에 붙는 시트**로 존재한다.

이번 라운드 범위는 **친구 등록**, **채팅**, **선물하기** 세 가지다. 캘린더는 다음 슬라이스다.

두 가지 모드로 돈다:

- **데모 모드(기본)** — 서버 없이 한 브라우저 안에서 localStorage + BroadcastChannel 로 동작한다.
- **서버 모드** — `VITE_API_BASE` 를 백엔드로 향하게 하면, 진짜 서버(Fastify + PostgreSQL +
  REST + WebSocket)가 시스템 오브 레코드가 된다. 다른 기기·다른 브라우저의 두 사람이 실제로
  대화하고 선물을 주고받는다. 백엔드는 `server/` 에 있다(자세한 내용은 `server/README.md`).

## 실행

```bash
npm install
npm run dev        # http://127.0.0.1:5273
```

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 (루프백만 바인딩) |
| `npm run demo` | 워크샵용 실패 시연 전체 실행 |
| `npm run build` | 타입체크 후 프로덕션 빌드 → `dist/` |
| `npm run preview` | 빌드 결과 확인 |
| `npm test` | Vitest 1회 실행 |
| `npm run typecheck` | 타입만 검사 |

실패 시연(워크샵용): `npm run demo`. 자세한 것은 `scripts/demo/README.md`를 참고한다.

## 두 사람이 실제로 대화하는 방법 (데모 모드)

`VITE_API_BASE` 가 없으면 서버 없이 한 브라우저 안에서 계정을 나눈다.

- **localStorage** — 세계(모든 사람·친구관계·대화·메시지). 탭끼리 공유한다.
- **sessionStorage** — 내가 누구인지. **탭마다 다르다.**
- **BroadcastChannel** — 상대가 보낸 메시지를 폴링 없이 즉시 받는 경로. 없으면 `storage` 이벤트로 대체된다.

따라서:

1. 탭 A 에서 이름을 넣어 계정을 만든다. 발급된 `HT-XXXX` 코드가 내 친구 코드다.
2. 탭 B 를 새로 열면 다시 로그인 화면이 나온다(sessionStorage 가 탭마다 다르므로). 다른 사람으로 들어간다.
3. 서로의 코드를 친구 추가에 입력한다.
4. 친구를 눌러 시트에서 **1:1 채팅** 을 시작하고 대화한다. 한쪽이 보내면 다른 탭에 바로 뜨고, 상대가 방을 보고 있으면 내 메시지에 **읽음** 이 붙는다.

데모 계정 4명이 미리 들어 있어 혼자서도 시험할 수 있다: 홍길동 `HT-GDNG`, 김철수 `HT-CHSU`,
이영희 `HT-YHEE`, 박영수 `HT-YSPK`. 코드는 `src/store/seed.ts` 한 곳에서만 관리한다.
이름은 예시용으로 통용되는 가명만 쓴다 — 레퍼런스 화면에 찍힌 실제 사람의 이름을 데모
데이터로 옮기지 않는다는 규칙이고, 그 이유는 옮기는 순간 리포에 남기 때문이다.

## 서버 모드 (진짜 백엔드에 붙이기)

`server/` 의 백엔드는 **시스템 오브 레코드**다: Fastify + PostgreSQL 위에서 REST 명령/조회와
WebSocket 실시간을 제공하고, 권한과 멱등성을 서버에서 강제한다. 선물 규칙·안읽음 계산 등
순수 도메인 코드(`src/domain/*`)는 프런트엔드와 서버가 **복사 없이 그대로** 공유한다.

프런트엔드는 `VITE_API_BASE` 가 설정되면 `ApiRepository`(`src/store/apiRepository.ts`)를 골라,
`GET /api/snapshot` 으로 인메모리 미러를 하이드레이트하고 `/ws` 푸시로 살아 있게 유지한다.
설정되지 않으면 `LocalRepository`(데모 모드)를 쓴다. `Repository` 의 스냅샷/구독은 동기라
렌더 경로가 두 구현에서 같고, 서버 권위가 필요한 사용자 생성·친구 코드는 `await` 가능한 결과를
돌려준다. 화면은 저장소가 로컬인지 서버인지 모른다.

### 로컬 개발 순서

```bash
# 1) PostgreSQL (로컬은 Docker, 아래 "배포 · 운영"의 주의 참고)
cd server
npm install
export DB_PASSWORD="$(openssl rand -hex 24)"
export COOKIE_SECRET="$(openssl rand -hex 32)"
npm run db:up                 # 127.0.0.1 에만 postgres 컨테이너 기동 (scripts/db.sh)

# 2) 백엔드 (위 환경변수를 이어받고, 부팅 시 자동 마이그레이션)
npm run dev                             # http://127.0.0.1:5311  (tsx watch)
curl -s http://127.0.0.1:5311/health   # => {"status":"ok"}

# 3) 프런트엔드 — API 를 백엔드로 향하게 하고 dev 서버 기동 (다른 터미널)
cd ..
VITE_API_BASE=http://127.0.0.1:5311 npm run dev   # http://127.0.0.1:5273
```

> 프런트엔드(S3+CloudFront)와 백엔드가 **다른 오리진**이면, 백엔드에
> `CLIENT_ORIGIN=https://<프런트 주소>` 를 주고(여러 개면 콤마로 구분) HTTPS 로 서비스한다
> (`COOKIE_SECURE=1`). 그러면 CORS 가 그 오리진만 허용하고 credentials 를 켜며, 세션 쿠키가
> `Secure; SameSite=None` 으로 나가 브라우저가 크로스 오리진 요청에 쿠키를 실어 보낸다.
> 로컬 개발처럼 동일 오리진(또는 http)이면 `CLIENT_ORIGIN` 을 비워 두면 된다.

이제 서로 다른 브라우저(또는 프로필)의 두 사람이 계정을 만들고, 친구 코드로 등록하고,
1:1 채팅에서 메시지를 주고받으며(WebSocket 으로 즉시 수신, 읽음 표시), 선물을 보내고 수락·
연장·환불까지 서버 위에서 진행한다.

### 환경변수

| 변수 | 어디서 | 기본값 | 설명 |
|---|---|---|---|
| `VITE_API_BASE` | 프런트엔드 | (없음) | 있으면 서버 모드(ApiRepository), 없으면 데모 모드(LocalRepository) |
| `PORT` | 백엔드 | `5311` | 서버 포트 |
| `HOST` | 백엔드 | `127.0.0.1` | 바인딩 호스트 |
| `DATABASE_URL` | 백엔드 | `DB_PASSWORD` 로 로컬 URL 조립 | 운영 PostgreSQL 접속 URL은 비밀 저장소에서 주입 |
| `DB_PASSWORD` | 백엔드/DB 스크립트 | (없음) | 로컬 Docker 전용. 소스 기본값 없이 명시적으로 설정 |
| `COOKIE_SECRET` | 백엔드 | 로컬은 프로세스별 무작위 값 | 운영에서는 32자 이상 값을 비밀 저장소에서 반드시 주입 |
| `CLIENT_ORIGIN` | 백엔드 | (없음) | 크로스 오리진 프런트엔드 주소(콤마 구분). 있으면 CORS 를 그 오리진만 허용+credentials, 쿠키 `SameSite=None` |
| `COOKIE_SECURE` | 백엔드 | `NODE_ENV=production` 이면 켜짐 | `1`=세션 쿠키에 `Secure` 강제. `CLIENT_ORIGIN` 과 함께 쓸 때 필수 |
| `DEV_TOOLS` | 백엔드 | (없음) | `1`(또는 `NODE_ENV=test`)이면 dev 전용 엔드포인트 개방: seed/reset, 사용자 디렉터리(`/api/dev/users`), 그리고 **기존 임의 사용자로의 `{userId}` 로그인**(운영엔 없음) |

### 백엔드 아키텍처 요약

- **Fastify + PostgreSQL + REST + WebSocket.** 명령/조회는 REST, 실시간은 `/ws`.
- **세션 쿠키 인증.** 서명·HttpOnly·SameSite 쿠키(`ht_session`)의 userId 가 **행위자 정체성의
  유일한 근거**다. 어떤 명령도 요청 바디의 user/actor id 를 권한 판단에 쓰지 않는다. 운영에서는
  `Secure`(HTTPS 전용)로 나가고, 크로스 오리진 배포면 `SameSite=None` 으로 나간다.
- **로그인 모델.** 운영 로그인은 항상 **새 사용자(새 세션)** 를 만든다. 비밀번호 없이 기존 임의
  사용자로 바로 들어가는 `{userId}` 경로는 데모/개발(`DEV_TOOLS`)에서만 열린다 — 운영에서는 403.
  로그인 화면의 "이미 있는 사람으로 들어가기" 목록도 dev 전용 `/api/dev/users` 로만 채워진다.
- **읽기 스코핑.** `GET /api/snapshot` 은 **행위자 자신의 세계**만 돌려준다: 본인 + 친구/대화
  상대 + 본인의 친구관계 + 본인이 속한 방과 그 방의 메시지·읽음 + 본인이 당사자인 선물. 로그인만
  하면 남의 메시지·선물 원장까지 다 읽히는 일이 없다.
- **도메인 코드 재사용.** 선물 상태전이·정산은 오직 `src/domain/gift.ts` 의
  `checkGiftAction`/`applyGiftAction` 이 만든다. 서버는 주문을 읽어 넘기고 결과를 저장할 뿐,
  전이·원장을 손으로 다시 만들지 않는다. 셀렉터(단방향 친구·1:1 방 유일성·안읽음 계산)도 그대로 쓴다.
- **단일 인스턴스 인메모리 WS 팬아웃.** 실제 상태가 바뀐 뮤테이션에서만 `{type:'change', scope}`
  를 브로드캐스트한다(무의미한 재렌더 루프 방지). 신호는 델타가 아니라 scope 힌트뿐이라, 신호를
  받은 클라이언트는 스코핑된 스냅샷을 다시 받아 미러를 재조정한다(부분 갱신이 아님). **데모
  규모에서는 충분하지만** 연결 수·변경 빈도가 커지면 매 변경마다 스냅샷 재요청이 부담이 된다 —
  이때는 (a) scope 별 델타 푸시, (b) 다중 인스턴스 팬아웃용 Redis Pub/Sub 이 향후 경로다.
  **아직 Redis 는 없다**(단일 인스턴스).
- **멱등성 보장.** 메시지·선물 전송은 `clientKey` 로, 1:1 방 열기는 두 사람 쌍 키로 중복을 막는다
  — 재시도해도 메시지·선물·방이 중복 생성되지 않는다. **동시 재시도**도 안전하다: 같은
  `(scope, actor, key)` 에 대해 트랜잭션 스코프 advisory 락으로 조회·실행·저장을 원자적으로
  직렬화하므로, 겹쳐 들어온 재시도가 부수효과를 두 번 내지 못한다.
- **서버측 권한 보장.** 방 멤버가 아닌 사람의 전송, 선물 당사자가 아닌 사람 또는 잘못된 행위자의
  선물 동작은 도메인 사유로 거절되고 상태를 바꾸지 않는다.
- **데모 전용은 운영에서 막혀 있다.** `FORCE_EXPIRE` 선물 동작은 API 경계에서 400 으로 거절되고,
  seed/reset 은 `DEV_TOOLS`/테스트에서만 열린다 — **운영에는 reset 이 없다.**
- **헬스체크.** `GET /health` → `{"status":"ok"}`.

전체 엔드포인트 표와 스키마 설명은 `server/README.md` 에 있다.

## 구조

```
src/
  domain/     타입과 순수 셀렉터. DOM·React·저장소를 모른다. (프런트·서버 공유)
  store/      Repository 인터페이스 + localStorage/Api 구현 + React 바인딩
  features/   화면 (auth / friends / chats / more / shell)
  ui/         Avatar, Sheet, 시간 표기
server/
  src/        Fastify 앱 · 서버 저장소 · DB 풀/스키마 · 실시간 허브
  test/       진짜 PostgreSQL 통합 테스트 (자체 완결 DB 하네스)
  scripts/    db.sh (로컬 Docker Postgres), e2e.ts (엔드투엔드 검증)
```

`store/repository.ts` 의 `Repository` 가 **유일한 데이터 창구**다. UI 는 저장소가 localStorage 인지
서버인지 모른다. 데모 모드는 `LocalRepository`, 서버 모드는 `ApiRepository` 가 같은 인터페이스를
구현하고, `StoreProvider` 가 `VITE_API_BASE` 유무로 하나를 고른다(테스트는 `repository?` prop 으로 주입).

### 알아둘 설계 결정

- **친구 관계는 단방향이다.** 내가 등록해도 상대의 친구 목록에는 내가 없다. 카카오톡과 같고,
  그래서 "나를 추가한 친구" 섹션이 성립한다.
- **1:1 방은 두 사람당 하나다.** `openDirectChat` 은 있으면 그 방을, 없으면 새로 만들어 돌려준다.
- **안읽음은 저장하지 않고 계산한다.** 대화방별 `lastReadAt` 하나만 두고 그 이후에 온 남의
  메시지를 센다. 카운터를 따로 들고 있으면 반드시 틀어진다.
- **내용이 바뀌지 않은 쓰기는 알림을 내지 않는다.** 이 규칙이 없으면 "방을 보고 있으면 읽음 처리"
  같은 효과가 자기 자신을 깨워 무한 루프가 된다(실제로 React #185 로 한 번 터졌다).

## 선물하기

친구 프로필 시트의 `🎁 선물하기` 나 더보기 탭의 아이콘 그리드에서 열린다. 열리면 **전체 화면
서브앱**이 되어 자기 상단바와 자기 하단 탭(홈·카테고리·선물함·마이)을 갖는다.

B안을 버린 것이 아니다. B안의 주장은 **진입이 사람에서 온다**는 것이고 그건 그대로다 —
하단 탭은 여전히 5개이고 선물하기 탭은 없다. 열린 뒤의 표면 크기는 B안의 주장이 아니었고,
2열 상품 그리드는 시트 높이에서 성립하지 않는다. 실제 카카오톡도 같은 구조다: 진입은 관계에서
(홈 최상단이 "선물할 친구를 선택해 주세요"), 목적지는 자체 탭을 가진 전체 화면.

화면별 구조 분석은 `references/gift/NOTES.md` 에 있다. 참고했던 스크린샷 원본은 실제 사용자의
이름과 프로필 사진이 찍혀 있어 리포에 두지 않는다 — `.gitignore` 가 막고 있고, 개발에 필요한
정보 계층은 그 문서가 텍스트로 들고 있다.

### 주문의 생애

`src/domain/gift.ts` 가 상태기계를 순수 함수로 들고 있다. 저장되는 상태는 4개다:
`paid` → `accepted` → `used`, 그리고 종료 상태 `refunded`.

- **`expired` 는 저장하지 않고 계산한다.** 교환권 만료 시각이 지났으면 만료다. 안읽음을
  저장하지 않는 것과 같은 이유로, 저장하면 "만료로 바꿔주는 사람"이 필요해지고 그 사람이
  없는 순간 틀어진다.
- **`draft` 도 저장하지 않는다.** 결제 전은 보내기 시트를 닫으면 사라지는 화면 상태다.
- **`cancelled` 를 따로 두지 않는다.** 취소는 곧 환불이고, 다른 점은 사유(`closedBy`)뿐이다.

규칙:

| 상황 | 결과 |
|---|---|
| 수락 | 유효기간 90일 교환권 발급, **소유권이 받는 사람에게 이전** |
| 수락 **전** 보낸 사람 취소 | 전액 환불 |
| 수락 **후** 보낸 사람 취소 | **불가** — 이미 받는 사람 것이다 |
| 받는 사람이 받은 선물 취소 | 전액 환불, **돈은 결제한 사람에게** |
| 연장 | 남은 기간에 +90일, **1회만** |
| 만료 후 환불 | 90% (10% 수수료), 보낸 사람만 신청 |
| 사용 완료 | 종료. 이후 환불·취소 모두 불가 |

`checkGiftAction(order, action, actor, now)` 이 "지금 이 사람이 이 동작을 할 수 있는가"를
답하고, 화면은 **버튼을 비활성화할 때도 같은 함수를 쓴다** — 그래서 비활성 이유와 실제 거절
이유가 같은 문장이다. 규칙이 두 곳에 적히면 반드시 어긋난다.

만료·환불 경로를 실제로 눌러보려면 90일을 기다릴 수 없으므로, 교환권 시트에
`데모: 유효기간이 지난 것으로 하기` 를 두었다.

### 채팅과의 연동

선물을 보내면 1:1 방(없으면 새로 만들어)에 **선물 버블**이 생긴다. 버블은 상태를 저장된
텍스트로 굳히지 않고 주문에서 매번 읽으므로, 받는 쪽이 버블에서 바로 수락하면 그 자리에서
`사용중 · 90일 남음` 으로 바뀌고 다른 탭에도 즉시 반영된다. 수락 알림용 시스템 메시지를
따로 흘리지 않는 것은 대화를 지저분하게 만들지 않으려는 선택이다.

### 상품 카탈로그

`src/domain/products.ts` 에 24개 상품, 15개 테마, 8개 카테고리가 있다. **저장소(`Db`)에
넣지 않는다** — 카탈로그는 사용자 데이터가 아니고, localStorage 에 복사하면 코드에서 상품을
고칠 때마다 저장된 사본과 어긋난다. 주문은 `productId` 와 **결제 당시 가격**을 함께 들고
있어서 카탈로그가 바뀌어도 이미 보낸 선물의 정산은 흔들리지 않는다.

브랜드명은 전부 가상 상호이고 상품 사진은 쓰지 않는다. 이모지 한 글자와 배경색으로 자리를
채운다 — 아바타에서 쓰는 방식과 같다.

## 한계 (알고 남겨둔 것)

- **데모 모드에는 서버가 없다.** `VITE_API_BASE` 없이 쓰면 같은 브라우저 안에서만 동작한다 — 다른
  기기에서는 서로 보이지 않고, 브라우저 데이터를 지우면 사라진다. **서버 모드(위 "서버 모드")를 켜면
  진짜 백엔드가 시스템 오브 레코드가 되어 이 한계가 사라진다.** 아래 두 한계(동시 쓰기 경합, 약한 인증)도
  데모 모드 한정이다: 서버는 트랜잭션으로 경합을 없애고 세션 쿠키를 유일한 행위자 근거로 삼는다.
- **동시 쓰기 경합(데모 모드)이 남아 있다.** 읽고-고쳐-쓰기 구조라 두 탭이 같은 순간에 쓰면 한쪽이
  덮일 수 있다. 쓰기 직전에 저장소를 다시 읽어 창을 좁혔지만 없애지는 못했다. 서버 모드에서는 사라진다.
- **인증이 약하다.** 이름만 넣으면 누구든 되고, 데모 모드는 계정 목록에서 아무 사람으로나 들어갈 수 있다.
  서버 모드도 비밀번호는 없지만(데모 목적) 서명·HttpOnly 세션 쿠키가 행위자 정체성의 유일한 근거이고
  권한은 서버에서 강제된다. 어느 쪽이든 이대로 공개 서비스에 올려서는 안 된다.
- **딥링크가 없다.** 탭·대화방 상태가 URL 에 없어서 새로 고치면 첫 화면으로 돌아간다.
- **그룹 채팅은 자료 구조만 있다.** `Chat.memberIds` 가 3명 이상을 담을 수 있고 화면도 인원수를
  표시하지만, 방을 만드는 경로는 아직 없다.
- **일정은 자리만 잡혀 있다.** 친구 프로필 시트의 `📅 약속 잡기` 는 눌리지 않는다. 위치 자체가
  B안의 주장이라 비워두지 않았다.
- **선물하기에 위시리스트와 검색이 없다.** 레퍼런스 하단 탭의 `위시` 와 상단바 검색이 그 자리다.
  위시는 모델이 없어서, 검색은 카탈로그가 24개뿐이라 뺐다.
- **결제는 모의다.** 실제 결제·정산 연동은 없고 주문에 원장 기록만 남는다.

## 배포 (Terraform)

```bash
npm run build                 # dist/ 를 먼저 만든다
cd infra-tf
terraform init                # 최초 1회
terraform plan -out=tfplan
terraform apply tfplan
```

| 항목 | 값 |
|---|---|
| 계정 · 리전 | `<AWS_ACCOUNT_ID>` · ap-northeast-2 (CloudFront 는 글로벌) |
| 버킷 | `hello-talk-site-<AWS_ACCOUNT_ID>-<random>` — 퍼블릭 전면 차단, AES256 |
| CloudFront | 배포 1개, PriceClass_200, HTTP/2+3 |
| 상태 파일 | `infra-tf/terraform.tfstate` (로컬) |

버킷 이름은 `variables.tf` 의 `name` 과 계정 번호, 그리고 무작위 접미사로 조립된다 —
S3 버킷 이름은 전역에서 유일해야 하므로 계정 번호를 섞는다. 실제 계정 번호와 배포 ID,
공개 URL 은 이 문서에 적지 않는다: 인증이 없는 공개 데모라서, 표적이 될 식별자를
리포에 함께 두지 않는다. 배포하면 `terraform output` 이 알려준다.

```bash
cd infra-tf && terraform output
# site_url / bucket_name / distribution_id / uploaded_files
```

구성은 프라이빗 S3 + CloudFront + OAC 다. S3 정적 웹사이트 호스팅은 켜지 않는다 —
그 엔드포인트는 퍼블릭 HTTP 라서 "퍼블릭 차단 + OAC 로만 읽기"와 어긋난다.
버킷 정책은 이 배포 하나만 `s3:GetObject` 로 허용하고, HTTPS 아닌 요청은 Deny 한다.
실측으로 S3 직접 접근은 403, CloudFront 경유는 200 이다.

**재배포는 `npm run build` 후 `terraform apply` 만 하면 된다.** 무효화가 필요하지 않다:
`/assets/*` 는 파일명에 콘텐츠 해시가 있어 내용이 바뀌면 URL 이 바뀌고(1년 immutable),
`index.html` 은 `no-cache` 라 CloudFront 가 매번 재검증한다.

### 되돌리기

```bash
cd infra-tf && terraform destroy
```

버킷은 `force_destroy = true` 라 객체까지 함께 지워진다. CloudFront 삭제는 disable
전파에 15~20분 걸린다. **`terraform.tfstate` 를 지우면 안 된다** — 지우면 만든 리소스를
더 이상 추적하지 못하고 destroy 도 못 한다.

### 왜 Terraform 인가 (CDK 대비)

CDK 버전도 한 번 작성했지만 **지웠다.** 같은 리소스를 두 도구가 각자 소유하면 상태가
어긋나 위험하므로 하나만 남겨야 한다. Terraform 을 고른 실질적 이점은 파일 업로드다 —
CDK 의 `BucketDeployment` 는 업로드를 위해 Lambda 1개 + 레이어 2개 + IAM 역할·정책을
함께 만드는데, Terraform 은 `aws_s3_object` 로 직접 올려 그 부수 리소스가 전부 없다.
이 배포의 13개 리소스 중 실제 인프라는 10개, 나머지 3개는 업로드된 파일 자체다.

권한 경로도 다르다. CDK 는 부트스트랩 역할(`cdk-hnb659fds-deploy-role`)을 빌려
CloudFormation 에 위임하고, Terraform 은 인스턴스 역할로 S3·CloudFront API 를 직접
호출한다. 이 계정의 `daily-puzzle-crew-role` 은 후자도 통과한다(실측 완료).

### 보안상 알아둘 것

이 배포는 **인증이 없는 공개 데모**다. 링크를 아는 사람은 누구나 접속해 아무 이름으로
계정을 만들거나 계정 목록에서 다른 사람으로 전환할 수 있다. 데이터는 방문자 각자의
브라우저에만 남아 서로의 대화가 섞이지는 않지만, 실서비스로 올릴 구성은 아니다.

### 백엔드 배포 (계획 · 아직 적용하지 않음)

프런트엔드는 위처럼 **프라이빗 S3 + CloudFront**(`infra-tf`)에 그대로 둔다. 백엔드는 정적
자산이 아니므로 **별도 서비스**로 배포한다. 지향하는 운영 자세는 다음과 같다:

- **관리형 PostgreSQL 을 따로 프로비저닝**한다(정적 프런트엔드와 분리). dev/prod 를 격리하고,
  접속 문자열·`COOKIE_SECRET` 등 비밀은 **관리형 시크릿 저장소**로 주입한다(리포에 넣지 않는다).
- **DB 백업**, **로그·모니터링**, **헬스체크**(`GET /health` 이미 있음)를 붙인다.
- 단일 인스턴스 인메모리 WS 팬아웃을 다중 인스턴스로 확장하려면 **Redis Pub/Sub** 이 향후 경로다
  (지금은 없다).

> **아직 정하지 않은 것 · 미룬 것.** 백엔드를 올릴 구체적인 **AWS 컴퓨트 서비스는 아직 결정하지
> 않았다.** 그래서 이 문서는 백엔드용 Terraform 을 짐작으로 쓰지 않는다. 백엔드 IaC 는 **보류**다 —
> 이 환경에는 Terraform CLI 가 설치되어 있지 않고(프런트엔드 `infra-tf` 도 여기서 apply 하지 않는다),
> 컴퓨트 선택이 확정되기 전에 추측성 인프라 코드를 남기지 않는다. 컴퓨트가 정해지면 그때 별도의
> 백엔드 IaC 를 추가한다.

### 엔드투엔드 (server/)

```bash
cd server
npm run e2e        # 진짜 서버 + 진짜 PostgreSQL + 진짜 WebSocket 을 상대로 두 세션 흐름 검증
```

`scripts/e2e.ts` 가 DB 자식 프로세스 + Fastify(in-process, 실제 포트 listen) + WebSocket 클라이언트
두 개를 **한 프로세스 안에서** 띄우고, 쿠키 항아리 두 개로 두 세션(A·B)을 몰아 전체 흐름을 단언한다:
사용자 A·B 생성(서버 발급 코드) → A 가 B 를 친구 코드로 등록(단방향) → 1:1 방 열기(멱등) → A 메시지
전송·B 가 WebSocket 푸시로 수신·읽음 상태(B 안읽음 증가→markRead 로 0, A 가 B 의 읽음 확인, no-op
markRead 는 브로드캐스트 없음) → A 가 B 에게 선물(주문+선물 메시지 원자적 안착) → B 수락(90일 교환권·
소유권 이전) → 연장 1회 → 권한 실패(제3자·잘못된 행위자 거절, 상태 불변)·FORCE_EXPIRE 400·멱등.
실패하면 nonzero 로 종료한다. 마지막 실행은 **52건 단언 통과**했다.

> 왜 한 프로세스 안에서 다 하나: 이 실행 환경의 각 셸 명령은 수명이 짧은 PID·네트워크 네임스페이스에서
> 돌아, 한 명령에서 띄운 서버를 다른 명령에서 붙을 수 없다(127.0.0.1 = EHOSTUNREACH). 그래서 DB·서버·
> WS 클라이언트를 모두 한 번의 실행 수명 안에 둔다. 통합 테스트도 같은 이유로 DB 를 자식 프로세스로 띄운다.
