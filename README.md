# hello-talk

카카오톡 스타일 메신저. 화면 배치는 프로토타입에서 고른 **B안(관계에서 파생 · 새 목적지 없음)** 을 따른다:
하단 탭은 5개 그대로 두고, 선물하기와 일정은 별도 탭이 아니라 **사람과 대화에 붙는 시트**로 존재한다.

이번 라운드 범위는 **친구 등록**, **채팅**, **선물하기** 세 가지다. 캘린더는 다음 슬라이스다.

## 실행

```bash
npm install
npm run dev        # http://127.0.0.1:5273
```

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 (루프백만 바인딩) |
| `npm run build` | 타입체크 후 프로덕션 빌드 → `dist/` |
| `npm run preview` | 빌드 결과 확인 |
| `npm test` | Vitest 1회 실행 |
| `npm run typecheck` | 타입만 검사 |

## 두 사람이 실제로 대화하는 방법

서버가 없다. 대신 한 브라우저 안에서 계정을 나눈다.

- **localStorage** — 세계(모든 사람·친구관계·대화·메시지). 탭끼리 공유한다.
- **sessionStorage** — 내가 누구인지. **탭마다 다르다.**
- **BroadcastChannel** — 상대가 보낸 메시지를 폴링 없이 즉시 받는 경로. 없으면 `storage` 이벤트로 대체된다.

따라서:

1. 탭 A 에서 이름을 넣어 계정을 만든다. 발급된 `HT-XXXX` 코드가 내 친구 코드다.
2. 탭 B 를 새로 열면 다시 로그인 화면이 나온다(sessionStorage 가 탭마다 다르므로). 다른 사람으로 들어간다.
3. 서로의 코드를 친구 추가에 입력한다.
4. 친구를 눌러 시트에서 **1:1 채팅** 을 시작하고 대화한다. 한쪽이 보내면 다른 탭에 바로 뜨고, 상대가 방을 보고 있으면 내 메시지에 **읽음** 이 붙는다.

데모 계정 4명이 미리 들어 있어 혼자서도 시험할 수 있다: 홍길동 `HT-GDNG`, 김철수 `HT-CHSU`,
이영희 `HT-YHEE`, 박영수 `HT-YSPK`. 코드는 `src/store/seed.ts` 한 곳에서만 관리한다.
이름은 예시용으로 통용되는 가명만 쓴다 — 레퍼런스 화면에 찍힌 실제 사람의 이름을 데모
데이터로 옮기지 않는다는 규칙이고, 그 이유는 옮기는 순간 리포에 남기 때문이다.

## 구조

```
src/
  domain/     타입과 순수 셀렉터. DOM·React·저장소를 모른다.
  store/      Repository 인터페이스 + localStorage 구현 + React 바인딩
  features/   화면 (auth / friends / chats / more / shell)
  ui/         Avatar, Sheet, 시간 표기
```

`store/repository.ts` 의 `Repository` 가 **유일한 데이터 창구**다. UI 는 저장소가 localStorage 인지
서버인지 모른다. 서버를 붙일 때는 이 인터페이스를 구현한 클래스를 하나 더 만들어
`StoreProvider` 에 넘긴다.

### 알아둘 설계 결정

- **친구 관계는 단방향이다.** 내가 등록해도 상대의 친구 목록에는 내가 없다. 카카오톡과 같고,
  그래서 "나를 추가한 친구" 섹션이 성립한다.
- **1:1 방은 두 사람당 하나다.** `openDirectChat` 은 있으면 그 방을, 없으면 새로 만들어 돌려준다.
- **안읽음은 저장하지 않고 계산한다.** 대화방별 `lastReadAt` 하나만 두고 그 이후에 온 남의
  메시지를 센다. 카운터를 따로 들고 있으면 반드시 틀어진다.
- **내용이 바뀌지 않은 쓰기는 알림을 내지 않는다.** 이 규칙이 없으면 "방을 보고 있으면 읽음 처리"
  같은 효과가 자기 자신을 깨워 무한 루프가 된다(실제로 React #185 로 한 번 터졌다).

## 선물하기

친구 프로필 시트의 `🎁 선물하기` 나 더보기 탭의 아이콘 그리드에서 열린다. 열리면 **전체 화면
서브앱**이 되어 자기 상단바와 자기 하단 탭(홈·카테고리·선물함·마이)을 갖는다.

B안을 버린 것이 아니다. B안의 주장은 **진입이 사람에서 온다**는 것이고 그건 그대로다 —
하단 탭은 여전히 5개이고 선물하기 탭은 없다. 열린 뒤의 표면 크기는 B안의 주장이 아니었고,
2열 상품 그리드는 시트 높이에서 성립하지 않는다. 실제 카카오톡도 같은 구조다: 진입은 관계에서
(홈 최상단이 "선물할 친구를 선택해 주세요"), 목적지는 자체 탭을 가진 전체 화면.

화면별 구조 분석은 `references/gift/NOTES.md` 에 있다. 참고했던 스크린샷 원본은 실제 사용자의
이름과 프로필 사진이 찍혀 있어 리포에 두지 않는다 — `.gitignore` 가 막고 있고, 개발에 필요한
정보 계층은 그 문서가 텍스트로 들고 있다.

### 주문의 생애

`src/domain/gift.ts` 가 상태기계를 순수 함수로 들고 있다. 저장되는 상태는 4개다:
`paid` → `accepted` → `used`, 그리고 종료 상태 `refunded`.

- **`expired` 는 저장하지 않고 계산한다.** 교환권 만료 시각이 지났으면 만료다. 안읽음을
  저장하지 않는 것과 같은 이유로, 저장하면 "만료로 바꿔주는 사람"이 필요해지고 그 사람이
  없는 순간 틀어진다.
- **`draft` 도 저장하지 않는다.** 결제 전은 보내기 시트를 닫으면 사라지는 화면 상태다.
- **`cancelled` 를 따로 두지 않는다.** 취소는 곧 환불이고, 다른 점은 사유(`closedBy`)뿐이다.

규칙:

| 상황 | 결과 |
|---|---|
| 수락 | 유효기간 90일 교환권 발급, **소유권이 받는 사람에게 이전** |
| 수락 **전** 보낸 사람 취소 | 전액 환불 |
| 수락 **후** 보낸 사람 취소 | **불가** — 이미 받는 사람 것이다 |
| 받는 사람이 받은 선물 취소 | 전액 환불, **돈은 결제한 사람에게** |
| 연장 | 남은 기간에 +90일, **1회만** |
| 만료 후 환불 | 90% (10% 수수료), 보낸 사람만 신청 |
| 사용 완료 | 종료. 이후 환불·취소 모두 불가 |

`checkGiftAction(order, action, actor, now)` 이 "지금 이 사람이 이 동작을 할 수 있는가"를
답하고, 화면은 **버튼을 비활성화할 때도 같은 함수를 쓴다** — 그래서 비활성 이유와 실제 거절
이유가 같은 문장이다. 규칙이 두 곳에 적히면 반드시 어긋난다.

만료·환불 경로를 실제로 눌러보려면 90일을 기다릴 수 없으므로, 교환권 시트에
`데모: 유효기간이 지난 것으로 하기` 를 두었다.

### 채팅과의 연동

선물을 보내면 1:1 방(없으면 새로 만들어)에 **선물 버블**이 생긴다. 버블은 상태를 저장된
텍스트로 굳히지 않고 주문에서 매번 읽으므로, 받는 쪽이 버블에서 바로 수락하면 그 자리에서
`사용중 · 90일 남음` 으로 바뀌고 다른 탭에도 즉시 반영된다. 수락 알림용 시스템 메시지를
따로 흘리지 않는 것은 대화를 지저분하게 만들지 않으려는 선택이다.

### 상품 카탈로그

`src/domain/products.ts` 에 24개 상품, 15개 테마, 8개 카테고리가 있다. **저장소(`Db`)에
넣지 않는다** — 카탈로그는 사용자 데이터가 아니고, localStorage 에 복사하면 코드에서 상품을
고칠 때마다 저장된 사본과 어긋난다. 주문은 `productId` 와 **결제 당시 가격**을 함께 들고
있어서 카탈로그가 바뀌어도 이미 보낸 선물의 정산은 흔들리지 않는다.

브랜드명은 전부 가상 상호이고 상품 사진은 쓰지 않는다. 이모지 한 글자와 배경색으로 자리를
채운다 — 아바타에서 쓰는 방식과 같다.

## 한계 (알고 남겨둔 것)

- **서버가 없다.** 같은 브라우저 안에서만 동작한다. 다른 기기·다른 브라우저에서는 서로 보이지 않고,
  브라우저 데이터를 지우면 함께 사라진다.
- **동시 쓰기 경합이 남아 있다.** 읽고-고쳐-쓰기 구조라 두 탭이 같은 순간에 쓰면 한쪽이 덮일 수 있다.
  쓰기 직전에 저장소를 다시 읽어 창을 좁혔지만 없애지는 못했다. 서버나 단일 쓰기 잠금이 붙으면 사라진다.
- **인증이 없다.** 이름만 넣으면 누구든 되고, 계정 목록에서 아무 사람으로나 들어갈 수 있다.
  데모를 굴리기 위한 의도된 선택이며, 이대로 공개 서비스에 올려서는 안 된다.
- **딥링크가 없다.** 탭·대화방 상태가 URL 에 없어서 새로 고치면 첫 화면으로 돌아간다.
- **그룹 채팅은 자료 구조만 있다.** `Chat.memberIds` 가 3명 이상을 담을 수 있고 화면도 인원수를
  표시하지만, 방을 만드는 경로는 아직 없다.
- **일정은 자리만 잡혀 있다.** 친구 프로필 시트의 `📅 약속 잡기` 는 눌리지 않는다. 위치 자체가
  B안의 주장이라 비워두지 않았다.
- **선물하기에 위시리스트와 검색이 없다.** 레퍼런스 하단 탭의 `위시` 와 상단바 검색이 그 자리다.
  위시는 모델이 없어서, 검색은 카탈로그가 24개뿐이라 뺐다.
- **결제는 모의다.** 실제 결제·정산 연동은 없고 주문에 원장 기록만 남는다.

## 배포 (Terraform)

```bash
npm run build                 # dist/ 를 먼저 만든다
cd infra-tf
terraform init                # 최초 1회
terraform plan -out=tfplan
terraform apply tfplan
```

| 항목 | 값 |
|---|---|
| 계정 · 리전 | `<AWS_ACCOUNT_ID>` · ap-northeast-2 (CloudFront 는 글로벌) |
| 버킷 | `hello-talk-site-<AWS_ACCOUNT_ID>-<random>` — 퍼블릭 전면 차단, AES256 |
| CloudFront | 배포 1개, PriceClass_200, HTTP/2+3 |
| 상태 파일 | `infra-tf/terraform.tfstate` (로컬) |

버킷 이름은 `variables.tf` 의 `name` 과 계정 번호, 그리고 무작위 접미사로 조립된다 —
S3 버킷 이름은 전역에서 유일해야 하므로 계정 번호를 섞는다. 실제 계정 번호와 배포 ID,
공개 URL 은 이 문서에 적지 않는다: 인증이 없는 공개 데모라서, 표적이 될 식별자를
리포에 함께 두지 않는다. 배포하면 `terraform output` 이 알려준다.

```bash
cd infra-tf && terraform output
# site_url / bucket_name / distribution_id / uploaded_files
```

구성은 프라이빗 S3 + CloudFront + OAC 다. S3 정적 웹사이트 호스팅은 켜지 않는다 —
그 엔드포인트는 퍼블릭 HTTP 라서 "퍼블릭 차단 + OAC 로만 읽기"와 어긋난다.
버킷 정책은 이 배포 하나만 `s3:GetObject` 로 허용하고, HTTPS 아닌 요청은 Deny 한다.
실측으로 S3 직접 접근은 403, CloudFront 경유는 200 이다.

**재배포는 `npm run build` 후 `terraform apply` 만 하면 된다.** 무효화가 필요하지 않다:
`/assets/*` 는 파일명에 콘텐츠 해시가 있어 내용이 바뀌면 URL 이 바뀌고(1년 immutable),
`index.html` 은 `no-cache` 라 CloudFront 가 매번 재검증한다.

### 되돌리기

```bash
cd infra-tf && terraform destroy
```

버킷은 `force_destroy = true` 라 객체까지 함께 지워진다. CloudFront 삭제는 disable
전파에 15~20분 걸린다. **`terraform.tfstate` 를 지우면 안 된다** — 지우면 만든 리소스를
더 이상 추적하지 못하고 destroy 도 못 한다.

### 왜 Terraform 인가 (CDK 대비)

CDK 버전도 한 번 작성했지만 **지웠다.** 같은 리소스를 두 도구가 각자 소유하면 상태가
어긋나 위험하므로 하나만 남겨야 한다. Terraform 을 고른 실질적 이점은 파일 업로드다 —
CDK 의 `BucketDeployment` 는 업로드를 위해 Lambda 1개 + 레이어 2개 + IAM 역할·정책을
함께 만드는데, Terraform 은 `aws_s3_object` 로 직접 올려 그 부수 리소스가 전부 없다.
이 배포의 13개 리소스 중 실제 인프라는 10개, 나머지 3개는 업로드된 파일 자체다.

권한 경로도 다르다. CDK 는 부트스트랩 역할(`cdk-hnb659fds-deploy-role`)을 빌려
CloudFormation 에 위임하고, Terraform 은 인스턴스 역할로 S3·CloudFront API 를 직접
호출한다. 이 계정의 `daily-puzzle-crew-role` 은 후자도 통과한다(실측 완료).

### 보안상 알아둘 것

이 배포는 **인증이 없는 공개 데모**다. 링크를 아는 사람은 누구나 접속해 아무 이름으로
계정을 만들거나 계정 목록에서 다른 사람으로 전환할 수 있다. 데이터는 방문자 각자의
브라우저에만 남아 서로의 대화가 섞이지는 않지만, 실서비스로 올릴 구성은 아니다.
