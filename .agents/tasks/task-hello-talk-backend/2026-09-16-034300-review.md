# Backend review fixes — scoped snapshot, gated demo login, CORS/secure cookie, atomic idempotency, stable chat id — review (v2)

The fix commit (`4e516e5`) addresses the seven concerns from v1. `GET /api/snapshot` now returns a per-actor scoped view instead of the whole database; the passwordless `{userId}` login is gated behind `devTools` (403 in production) with a separate dev-only `/api/dev/users` directory; `@fastify/cors` is registered with a `CLIENT_ORIGIN` allowlist and `credentials:true`; the session cookie gets `Secure` (and `SameSite=None` cross-origin) in production; `withIdempotency` now holds a transaction-scoped advisory lock so concurrent retries serialize; and `ApiRepository.openDirectChat` keeps a stable temp id, aliasing the server id both outbound and on incoming snapshots. A new `server/test/security.test.ts` covers all of these, and the domain invariants (synchronous `Repository`, domain-only gift rules, directional friendships, unique direct chats, computed unread, restricted stored statuses, `FORCE_EXPIRE` rejection, no prod reset) are untouched by the fixes.

Watch for: the scoped snapshot closed the read-authorization hole, but it also emptied the frontend demo login list — `LoginScreen` builds "이미 있는 사람으로 들어가기" from `db.users`, which in server mode is only populated after login and then only with the actor's own counterparts; the new `/api/dev/users` directory endpoint exists on the server but no frontend code fetches it, so the picker is empty in server mode (confirmed, new regression). The idempotency advisory lock is correct despite running `fn()` on a separate pool connection (confirmed). No new security issues in the CORS/cookie handling (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The read-authorization boundary is now real. `scopedSnapshot(actorId)` selects only the chats the actor is a member of, the messages/reads in those chats, friendships where the actor is either party, gift orders the actor sent or received, and the union of users appearing in any of those. The v1 leak — any logged-in caller reading everyone's messages and gift ledgers — is closed, and the security test proves a third party C sees zero chats, messages, gifts, and only their own user record while A still sees their full world including counterpart B.

Session establishment is now gated. `POST /api/auth/session {userId}` returns 403 when `devTools` is off, so production login can only mint a fresh user via `{name}`; the demo directory that enumerated user ids is likewise dev-only (404 in prod). There is no alternate path to assume an existing identity in production.

The idempotency race is closed correctly. A dedicated "gate" connection opens a transaction, takes `pg_advisory_xact_lock` on a hash of `(scope, actor, key)`, then does lookup → execute → store → commit; concurrent retries block on the lock until the first commits and then read the stored result. The lock lives on the gate connection and `fn()`'s own transaction runs on a separate pooled connection, but that separation is fine — the gate serializes the whole critical section and only releases (commits) after the result is persisted.

The optimistic chat id is now stable. `openDirectChat` returns a temp id that never changes in the mirror; the server id is recorded in an alias map, translated onto outbound message/read requests, and folded back to the temp id when snapshots arrive, so a screen that navigated with the returned id never points at a ghost room and no duplicate room appears.

The remaining gap is one the scoping fix introduced on the frontend: the demo "sign in as an existing person" list has no data source in server mode. The server exposes `/api/dev/users` for exactly this, but `ApiRepository` never calls it and `LoginScreen` reads only the mirror's `db.users`.

### Scoped snapshot closes the read boundary without starving the mirror

`scopedSnapshot` runs three scoped selects in parallel — chats where the actor is a member (with aggregated `member_ids`), friendships where the actor is owner or friend, gift orders where the actor is sender or receiver — then pulls messages and reads for exactly those chat ids, and finally reads the union of all user ids that appeared (actor + chat members + friendship parties + gift parties). The frontend selectors need each counterpart's `User` record to render names, avatars, and friend rows, and that union guarantees they are present: a chat member, a friend, or a gift party always brings their user row along. The directional-friendship visibility is preserved on both sides — the `owner_id = $1 OR friend_id = $1` filter means the recipient of a one-way friendship still sees the edge (and the test asserts the reverse edge is absent), so `selectors` compute the same friend/unread state they did against the global snapshot.

The `ANY($1::text[])` messages/reads query tolerates an empty `chatIds` array (matches no rows), so a brand-new user with no chats gets an empty message set rather than an error.

### Advisory-lock idempotency is atomic across a connection split

The gate transaction (holding `pg_advisory_xact_lock`) and the command's own transaction (`this.tx`, via `fn()`) run on two different pooled connections — worth calling out because it looks wrong at first. It isn't: a second retry for the same `(scope, actor, key)` blocks at `pg_advisory_xact_lock` until the first gate commits, and only after that commit is the stored result visible, which the waiter reads and returns with `changed:false`. One residual: `fn()` commits its side effect before the key row is inserted, so a process crash between those two commits leaves a retry able to re-execute — the standard durability caveat of any store-after-effect scheme, not a concurrency double-execute. The FNV-1a hash to two int4 lock keys can collide two distinct keys onto the same lock, which only over-serializes, never under-serializes. Rejected validations skip the key insert and stay retryable. The concurrent-retry tests (four simultaneous messages, three simultaneous gifts) confirm exactly one row and one id.

### Stable optimistic chat id eliminates the ghost room

The temp id handed to the caller is never mutated; the server id is stored in `chatIdAliases`, applied via `toServerChatId` on outbound `messages`/`read` requests, and `replace` inverts the map to fold any server-id-keyed chat/message/read/gift-order in an incoming snapshot back to the temp id. A caller that captured the returned id before reconciliation keeps pointing at a live room, and no `srv-chat-*` duplicate appears — both asserted by the rewritten `openDirectChat` tests. The alias map is per-instance and grows over a session, but each entry is two short strings and a page reload starts clean (the reloaded snapshot uses server ids natively), so it is not a practical leak.

### CORS and cookie posture

CORS is registered only when `clientOrigins` is non-empty, echoing an allowlisted origin with `credentials:true` and rejecting others; the cookie flips to `SameSite=None; Secure` when a cross-origin client is configured and stays `Lax`/non-secure for local http, with `cookieSecure` deriving from `COOKIE_SECURE` and defaulting on under `NODE_ENV=production`. The cross-origin cookie needs `Secure`, and the prod-like path sets it, so the two settings do not contradict. The test matrix covers allow/deny preflight, the Secure+SameSite=None prod cookie, and the non-secure local cookie.

### Demo login list has no data source in server mode

`LoginScreen` computes `people` from `db.users` and renders a button per user for the "이미 있는 사람으로 들어가기" picker. In local mode the seed populates `db.users`, so the list works. In server mode the mirror hydrates from `GET /api/snapshot`, which requires a session and, once authenticated, returns only the actor plus their counterparts — never the full roster. Before any login there is no session, so the snapshot request is unauthorized and the mirror stays empty, leaving the picker with zero entries. The fix commit added `/api/dev/users` on the server precisely to back this list, and gated it to dev, but the frontend `ApiRepository` never requests it and `LoginScreen` was not changed to consume it. The result is that the documented demo affordance ("탭을 두 개 열어 서로 다른 사람으로 로그인") is unreachable through the UI in server mode — a user can only ever create a fresh account via `{name}`. The e2e passes because it posts to `/api/auth/session` and reads `/api/snapshot` directly with cookies; it never mounts `LoginScreen`, so this gap is invisible to it. Either `ApiRepository` should fetch `/api/dev/users` (when running against a dev backend) and merge it into the mirror so the picker is populated, or `LoginScreen` should hide the picker in server mode and lean on `{name}` sign-up — the `signInExisting` path itself still works for a known id, it is only the discovery list that is empty.
