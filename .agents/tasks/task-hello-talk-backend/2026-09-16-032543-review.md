# Real backend (Postgres + session auth + REST + WebSocket) for the frontend-only messenger — review (v1)

The change adds a Fastify + PostgreSQL backend under `server/` that becomes the system of record, and a frontend `ApiRepository` that implements the existing synchronous `Repository` interface against it. The backend reuses the frontend's pure domain code (`gift.ts`, `selectors.ts`, `products.ts`, `ids.ts`) rather than reimplementing rules, enforces authorization from the session cookie, and pushes change signals over a session-authenticated WebSocket with in-process fan-out. The frontend keeps an in-memory `Db` mirror hydrated from `GET /api/snapshot`, applies commands optimistically, and reconciles/rolls back against server responses. The domain invariants (directional friendships, unique direct chats, computed unread, stored gift statuses, refund-to-payer settlement) are preserved, and the `Repository` interface is genuinely unchanged (`git diff` on `repository.ts` is empty).

Watch for: session creation accepts a bare `{userId}` and issues a full session for any existing user with no secret (confirmed) — passwordless impersonation, and `GET /api/snapshot` hands every authenticated caller the entire database (confirmed), so the two together expose all users' messages and gifts. No CORS is registered while the client uses `credentials: 'include'` (confirmed), so a cross-origin `VITE_API_BASE` deployment cannot authenticate in a browser. The session cookie is never marked `secure` (confirmed). Idempotency does its lookup/insert outside the command transaction (confirmed), leaving a race window on concurrent retries.

**Verdict**: NEEDS_CHANGES

## High-level view

Actor identity is handled correctly at the command layer: every mutating route derives the actor from the signed session cookie via `requireUser`, and no command trusts an actor/owner id from the request body — `sendGift` forces `senderId = uid`, chat/friend/read/gift-action routes all key off `uid`. The weak point is not the command layer but session *establishment*: `POST /api/auth/session` with `{userId}` mints a session for any existing user id with no proof of ownership. That is the frontend's demo login model carried verbatim into a backend that now holds everyone's data.

Read authorization is absent. `GET /api/snapshot` returns the global `Db` — all users, all chats, all messages, all gift orders — to any authenticated session. The frontend mirror is designed around a global snapshot, so this is architectural, not a stray bug, but it means the backend is not enforcing any read boundary between actors.

Gift rules are faithfully reused — settlement and ownership live only in the domain, `FORCE_EXPIRE` is rejected at the API boundary, and there is no production reset. Direct-chat uniqueness is enforced by a partial unique index on `direct_pair_key`, and unread is computed server-side from a single `reads.last_read_at` per (chat, user), never stored as a counter — both invariants preserved.

The idempotency layer prevents duplicate message/gift creation on retry, but its read-then-run-then-write sequence is not inside a single transaction, so two simultaneous retries of the same client key can both miss the stored result and both execute.

Transport security has gaps that block the intended cross-origin deployment: no CORS plugin is registered even though the client sends `credentials: 'include'`, and the session cookie sets `httpOnly`/`sameSite=lax` but not `secure`.

The `ApiRepository` optimistic/reconcile/rollback logic is sound and preserves the no-emit-on-no-op discipline (`commit` compares serialized snapshots before notifying), but the optimistic `openDirectChat` returns a temp chat id that is later rewritten from the server id, and any screen that captured the temp id before reconciliation holds a stale reference.

<summary>Issues (7)</summary>

1. **Passwordless session by userId** — `POST /api/auth/session {userId}` issues a session for any existing user with no secret; combined with the global snapshot exposing every user id, this is full account impersonation. Gate it behind `devTools`, or require a real credential/token for existing-user login.
2. **Global snapshot, no read scoping** — `GET /api/snapshot` returns every user's chats, messages, and gifts to any authenticated caller. Scope the snapshot to the actor's own friends/chats/gifts, or document this as an accepted demo limitation.
3. **No CORS with credentialed fetch** — client uses `credentials: 'include'` but no CORS plugin is registered; a cross-origin `VITE_API_BASE` deployment cannot authenticate in a browser. Register `@fastify/cors` with an allowlisted origin and `credentials: true`.
4. **Session cookie not `secure`** — the cookie is `httpOnly`/`sameSite=lax` but never `secure`, so it can ride plaintext HTTP in production. Set `secure` when not in local dev.
5. **Idempotency race outside transaction** — `withIdempotency` reads and writes `idempotency_keys` in separate autocommit queries around `fn()`, so two concurrent retries with the same key can both execute. Do the lookup/insert and the command in one transaction, or insert the key first and let the unique constraint gate execution.
6. **Ghost temp chat id in ApiRepository** — `openDirectChat` returns a client-generated temp id that is rewritten once the server responds; a caller that navigates with the temp id before reconciliation points at a room id the server never knew. Consider resolving the server id before returning, or ensure all readers re-resolve via `directChatBetween`.
7. **Snapshot-only reconciliation on every change signal** — any mutation by any connected client triggers a full `GET /api/snapshot` refetch on all clients (fan-out carries only a scope hint, not a diff). Fine at demo scale; note it as a scaling limit.

### Actor identity is session-derived across all commands, but login is not

Every command route calls `requireUser` (signed cookie → user → 401 otherwise) and uses the returned `uid` as the actor; bodies never supply it — `sendGift` sets `senderId: uid`, `openDirectChat` uses `(uid, targetId)` so a caller cannot insert a third party, favorite/remove/read/gift-action all key off `uid`. Forged/unsigned cookies are rejected.

The gap is one level up. `POST /api/auth/session` with `{userId}` looks the user up and, if found, calls `setSession` for them — no password, no token, no prior session. Because `GET /api/snapshot` returns every user's `id`, any caller can enumerate ids and assume any identity. `auth.test.ts` asserts this path as intended, so it is a deliberate demo affordance — but it defeats the session-as-sole-identity model the rest of the backend is built around. Past a demo it must be gated (`devTools`) or replaced with a real credential exchange.

### Read authorization: the snapshot is global

```
GET /api/snapshot  ->  repo.snapshot()  ->  SELECT * FROM users / friendships / chats / messages / reads / gift_orders
```

The snapshot ignores the actor entirely and serializes the whole database. The frontend `ApiRepository` is built around exactly this — it hydrates a full `Db` mirror and runs the same selectors the local demo used — so scoping the snapshot per-actor would require the mirror to tolerate partial data. This is a design-level choice inherited from the local-first architecture, not an oversight in a single handler, but it means the backend enforces write authorization while performing no read authorization: any logged-in user can read all messages and gift ledgers of all users.

### Gift rules reused, not reimplemented

No party check, state check, or settlement math is duplicated server-side — `giftAction` loads the order `FOR UPDATE`, calls `applyGiftAction`, persists only on `ok`, and `sendGift` builds the order through `newGiftOrder`, so `checkGiftAction`'s receiver-only/sender-only rules and the refund-to-payer `settle` helper remain the single source. `FORCE_EXPIRE` is rejected at the route before reaching the domain. The `FOR UPDATE` lock serializes two parties racing on the same order so the second sees the committed new status — notably absent from the create paths (see idempotency below).

### Idempotency race window

`withIdempotency` keys on `(scope, actor_id, key)`, returns the stored result with `changed:false` on hit, and stores only when `ok !== false` so rejected validations stay retryable. But the lookup, the `fn()` execution, and the result insert are three separate pool queries, not one transaction. Two retries with the same key arriving together can both read "no existing key," both run the command (two messages / two gift orders), then both insert the key — `ON CONFLICT DO NOTHING` dedupes the *key* but not the two already-committed side effects. `sendGift`/`sendMessage` create fresh rows with no `FOR UPDATE` guard to narrow the window. Inserting the key first (and treating a conflict as "load and return the stored result") would close it.

### Ghost temp chat id in the mirror

Server-side uniqueness is solid: `openDirectChat` reads by `direct_pair_key`, inserts with `ON CONFLICT ... DO NOTHING RETURNING id`, and re-reads on a lost race, so concurrent opens converge on one room. The frontend optimistic version creates a temp room and later rewrites its id, migrating temp-keyed messages/reads — sound only as long as every reader re-resolves through `directChatBetween` rather than caching the temp id it was handed. A screen that navigated with the temp id before reconciliation points at a room the server never knew.

### ApiRepository optimistic model and no-op discipline

The no-emit-on-no-op guard carries into the API path: `commit` serializes and compares against the last emitted string, returning without notifying when content is unchanged. Rollback is symmetric — `onReject` reverts on non-2xx, `{ok:false}`, or network error, snapshotting the prior edge/order to restore. Reconnect re-runs `refresh()` on a 1.5s timer and chains snapshot refetches so overlapping signals don't reorder.

One residue: optimistic `createUser` inserts a provisional user with a client-generated id and swaps in the server's on success; on network failure the provisional lingers until the next snapshot. And every change signal — regardless of scope — triggers a full snapshot refetch on every connected client, since the fan-out payload is a scope string, not a delta (issue 7): a clear scaling boundary past single-instance demo.

### Transport security

The WebSocket authenticates from the signed cookie and closes unauthenticated connections with 1008. Two HTTP-side gaps: no CORS plugin is registered anywhere in `server/src` yet the client always sends `credentials: 'include'`, so the moment `VITE_API_BASE` points at a different origin the browser blocks the credentialed request — same-origin is the only working configuration today. And `setSession` omits `secure`, so nothing stops the session cookie from traversing plaintext HTTP. The default `cookieSecret` fallback is already flagged in config comments as must-override.

SQL is uniformly parameterized; the only interpolated identifier is the fixed `TRUNCATE` table list in the dev-gated `resetDatabase`, which takes no user input.
