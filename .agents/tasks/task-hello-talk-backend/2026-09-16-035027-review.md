# Demo login picker populated in server mode via dev user directory — review (v3)

The v2 pass approved the seven v1 fixes but flagged one regression: the scoped snapshot emptied the demo "이미 있는 사람으로 들어가기" picker in server mode, because before login there is no session (snapshot 401s) and after login the scoped snapshot only carries the actor's counterparts, and no frontend code fetched the dev-only `/api/dev/users` directory that was meant to back the list. Commit `e6b90cc` closes that gap on both ends: the server makes `GET /api/dev/users` session-optional (still `devTools`-gated), and `ApiRepository` gains an out-of-interface `loadDirectory()` — called once in the constructor — that fetches the directory and folds its rows into the mirror's `db.users` through the existing emit-on-change `mutate()`. `LoginScreen` and the synchronous `Repository` interface are unchanged.

Watch for: dropping `requireUser` from `/api/dev/users` widens who can read it, so the question is whether it leaks the data the scoped-snapshot fix was built to protect — it does not (confirmed): `allUsers()` returns only user directory rows (id, code, name, statusMessage, hue, createdAt) from a `users` table that holds no secrets and no messages/gifts/friendships, and the route stays 404 in production. The picker is now populated through a path the frontend actually exercises (confirmed). No new issues from `loadDirectory()` (confirmed).

**Verdict**: APPROVED

## High-level view

The regression is fixed end to end. `loadDirectory()` fetches `/api/dev/users` and merges the rows into `db.users` via `mutate`, which emits only when the serialized mirror changes; `LoginScreen` reads `db.users` straight from the store, so the picker fills in server/dev mode. Frontend tests drive exactly this: with the snapshot forced to 401 pre-login, the mirror still populates from the directory; with `devTools` off (404) it stays empty.

Making the directory session-optional does not reopen the read boundary. The endpoint returns only the minimal user directory — never the global `Db` — so it is not a backdoor to the messages, gifts, and friendships that the scoped snapshot protects. It remains `devTools`-gated, 404 in production, which is why the prod picker is correctly empty and prod users sign up via `{name}`.

Every v1/v2 invariant survives this commit untouched: the `{userId}` login still 403s in production, the snapshot stays session-gated and per-actor scoped, and the CORS, secure-cookie, atomic-idempotency, stable-chat-id, and domain rules are not in the diff. The only authorization removed is the session requirement on a dev-only directory, and the residual exposure is bounded to non-secret directory rows.

### loadDirectory / hydrate ordering does not clobber the picker

The constructor fires `loadDirectory()` and `hydrate()` without awaiting either, so their completion order is not fixed — worth checking because `hydrate()`'s `replace()` overwrites `next.users` wholesale from the snapshot, which could stomp the directory rows `loadDirectory()` folded in. Pre-login, `hydrate()` hits a 401 and returns before calling `replace()`, so it cannot clobber the directory rows during the window when the picker actually needs them. Post-login the snapshot carries only the actor and counterparts and would replace the broader directory set, but by then the picker has served its purpose and the logged-in user's own world is the content that should win.

### Session-optional directory is not a data backdoor

The concern with removing `requireUser` is whether `/api/dev/users` becomes an unauthenticated read into the data the scoped snapshot was built to protect. It does not. `allUsers()` runs `SELECT * FROM users ORDER BY created_at` and maps each row through `toUser`, yielding only `{ id, code, name, statusMessage, hue, createdAt }`. The `users` table schema carries no password, token, or session column — this is a passwordless demo identity model — and the endpoint returns `{ users }` alone, never the chats, messages, reads, friendships, or gift orders that live in other tables and that `scopedSnapshot` filters by actor. So the widened access exposes a user directory (names and friend codes), which is exactly what the login picker needs and no more; the messages/gifts/friendships boundary the v1 scoping fix established is untouched. The route stays inside the `if (deps.devTools)` guard, so it is not even registered in production (404), and the backend security test asserts precisely the intended asymmetry: `GET /api/dev/users` with no cookie returns 200 with the full name roster while `GET /api/snapshot` with no cookie returns 401.

### v1/v2 invariants unchanged by this commit

The only server edit is dropping the `requireUser` call inside the already-`devTools`-gated `/api/dev/users` handler. The `{userId}` session route still returns 403 when `devTools` is off, `/api/snapshot` still calls `requireUser` and returns the per-actor `scopedSnapshot`, and the CORS allowlist, secure/SameSite cookie logic, advisory-lock idempotency, stable optimistic chat id, and the domain rules (synchronous `Repository`, domain-only gift logic, directional friendships, unique direct chats, computed unread, `FORCE_EXPIRE` rejection, no prod reset) are not present in this diff and were confirmed intact in v2.
